Wiring an Eval Pipeline to the Claude API

The judge becomes a component when its verdict has a type

“Reply with JSON only” is a request, not a guarantee. Structured outputs turn the rubric into a contract the API enforces — and once the verdict is a typed object, the rest of the pipeline is a batch job and two ratios.

You have a prompt whose output quality you cannot write an assert for. “Did it answer the question?” and “did it stick to the source?” have no regex, so the usual move is to hand the grading to a second model: you write down what a good answer looks like — a rubric — paste in the candidate output, and ask for a verdict. The property this post grades is groundedness: every factual claim in an answer traceable to the text the system retrieved, with nothing invented in between.

The rubric ends in a line asking for JSON only. You json.loads() the reply and it works, for thirty-six cases. At case thirty-seven the answer arrives wrapped in a markdown fence and the harness dies.

“Reply with JSON only” is a request. A judge becomes a component the moment its verdict is a typed object the harness can fail on. (For how the surrounding pipeline is put together — criteria, test sets, where judges go wrong — see the previous post; nothing here depends on having read it.)

A schema turns the rubric into a contract

The fix is not a firmer instruction. The Claude API can constrain generation itself: you hand it a description of the shape you want, and the only text the model is allowed to produce is text that fits. That description is a JSON schema, and the easiest way to write one in Python is a Pydantic model — a class whose fields declare the types you expect. messages.parse() sends the schema along with the prompt and hands back a validated instance of that class, so the format instruction leaves the rubric entirely and the parse step disappears:

from typing import Literal

from anthropic import Anthropic
from pydantic import BaseModel, ConfigDict, ValidationError

client = Anthropic()

RUBRIC = """You are checking whether an ANSWER is fully supported by the CONTEXT.

CONTEXT:
{context}

ANSWER:
{answer}

Decompose the ANSWER into individual factual claims. A claim is supported only
if it is stated in or directly entailed by the CONTEXT. General knowledge does
not count as support. The verdict is "fail" if any claim is unsupported."""


class Verdict(BaseModel):
    """One judge's reading of one answer."""

    model_config = ConfigDict(extra="forbid")

    unsupported_claims: list[str]
    verdict: Literal["pass", "fail"]


def judge(context: str, answer: str) -> Verdict:
    """Score one answer for groundedness against its retrieved context."""
    try:
        response = client.messages.parse(
            model="claude-opus-5",
            max_tokens=16000,
            messages=[
                {"role": "user", "content": RUBRIC.format(context=context, answer=answer)}
            ],
            output_format=Verdict,
        )
    except ValidationError as exc:  # budget ran out mid-JSON: parse() raises
        raise RuntimeError(f"unparseable verdict: {exc}") from exc
    if response.parsed_output is None:  # refusal, or budget spent inside thinking
        raise RuntimeError(f"no verdict: {response.stop_reason}")
    return response.parsed_output

Field order carries weight. The schema fixes the order the model writes in, and unsupported_claims comes before verdict, so the judge commits to its evidence before it commits to a label.

max_tokens is generous for a reason. On this model it caps the reasoning the model does before answering and the reply itself, drawn from one budget. Running out fails two ways, and no single guard covers both: spend the budget inside the reasoning and there is no text at all, so parsed_output is None; spend it halfway through the JSON and parse() raises before there is a response object to inspect. A returned verdict looks like this:

Verdict(unsupported_claims=['Refunds can also be issued as store credit.'],
        verdict='fail')

A typed verdict is worth only as much as the cases you feed it.

The test set is the instrument, not the input

The data here is synthetic: six (context, answer) pairs I wrote by hand for this post. They stand in for a support assistant answering customer questions over a company’s own help-centre articles — context is the passage a retriever pulled from those articles, answer is what the assistant replied, and the label is the verdict a human reviewer gave it.

Three of the six are grounded. The other three each carry exactly one fabricated claim, phrased in the documentation’s own vocabulary — an invented processing time, say. That is the failure with money behind it: a customer told confidently that refunds land in three business days will act on it, and being wrong costs more than “I don’t know” would have. It is also the failure that no string-matching check catches, because a hallucination borrowing the source’s phrasing looks like the source.

Synthetic wins here because of what is being measured. The number this post is after is how often the judge agrees with a human, and that comparison needs cases whose correct verdict is already known — which is a labelled set, not a sample of production traffic. Two of the six, one of each kind:

CASES = [
    {
        "id": "refund-window-grounded",
        "context": "Refunds are available within 30 days of purchase. Once "
        "approved, the amount returns to the original payment method.",
        "answer": "You can request a refund within 30 days, and it goes back "
        "to the card you paid with.",
        "label": "pass",
    },
    {
        "id": "refund-window-invented-sla",
        "context": "Refunds are available within 30 days of purchase. Once "
        "approved, the amount returns to the original payment method.",
        "answer": "You can request a refund within 30 days. Refunds are "
        "processed within 3 business days.",
        "label": "fail",
    },
    # ...four more, three grounded and three ungrounded in total.
]

Caveat: six cases is a demonstration, not a calibration set

Six cases are enough to show the machinery and not enough to trust a number from. A calibration set — the labelled cases you measure the judge against — runs to fifty or a couple of hundred, and it is not a one-off: providers update models underneath you, so agreement has to be re-measured on a schedule rather than established once.

The scope is narrow in a second way. This measures the judge against the answers, and says nothing about the retriever that fetched the context in the first place. An answer can be perfectly grounded in a passage that was the wrong passage to pull, and this pipeline will call it a pass. Attributing that failure needs a separate scorer on the retrieval step.

Both limits are about how many cases you run and what you point them at, not about how you run them. The mechanics stay the same at six cases or two hundred — and at two hundred, how you run them starts to matter.

Batches turn the scoring loop into a job

Judges are the expensive part of a suite. Each case is its own API call, so a two-hundred-case suite scored in a loop is two hundred round trips, paid at full price and waited on one at a time. That cost is what quietly stops teams from running the suite on every change. The Batches API takes the other route: you submit every case at once as a single job, poll until it finishes, and pay half the per-token price for the privilege of not needing the answers immediately. Each request carries a custom_id, a label you choose that ties a result back to the case it came from:

import time

from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

batch = client.messages.batches.create(
    requests=[
        Request(
            custom_id=case["id"],
            params=MessageCreateParamsNonStreaming(
                model="claude-opus-5",
                max_tokens=16000,
                messages=[
                    {
                        "role": "user",
                        "content": RUBRIC.format(
                            context=case["context"], answer=case["answer"]
                        ),
                    }
                ],
                output_config={
                    "format": {
                        "type": "json_schema",
                        "schema": Verdict.model_json_schema(),
                    }
                },
            ),
        )
        for case in CASES
    ]
)

while client.messages.batches.retrieve(batch.id).processing_status != "ended":
    time.sleep(30)

The batch path asks for the schema differently. Instead of parse()’s output_format=, which takes the Pydantic class, it takes output_config.format and a raw JSON schema — hence the model_json_schema() call. extra="forbid" on the model is what makes that schema legal: the API only accepts schemas from a strict subset, and the strict subset requires additionalProperties: false, which is the JSON-schema way of saying no keys beyond the declared ones. Pydantic writes that line into the schema only when the model forbids extras.

Results come back in whatever order they finished, not the order you submitted, so every case is looked up by custom_id:

verdicts = {}
for result in client.messages.batches.results(batch.id):
    if result.result.type == "errored":
        raise RuntimeError(f"{result.custom_id}: {result.result.error}")
    if result.result.type != "succeeded":
        raise RuntimeError(f"{result.custom_id}: {result.result.type}")
    message = result.result.message
    if message.stop_reason != "end_turn":
        raise RuntimeError(f"{result.custom_id}: stopped on {message.stop_reason}")
    text = next((b.text for b in message.content if b.type == "text"), None)
    if text is None:
        raise RuntimeError(f"{result.custom_id}: completed turn with no text block")
    verdicts[result.custom_id] = Verdict.model_validate_json(text)

labels = {case["id"]: case["label"] for case in CASES}
pass_rate = sum(v.verdict == "pass" for v in verdicts.values()) / len(verdicts)
agreement = sum(verdicts[i].verdict == labels[i] for i in labels) / len(labels)

succeeded is a transport verdict, not a content one. It means the request reached the model and came back, which is not the same as the model having produced a usable answer: a case the model refused, or one that ran out of budget mid-sentence, still lands in succeeded with no text block or half of one. That is what the stop_reason check is for — stop_reason is the API’s account of why the model stopped, and end_turn is the only value that means it finished on its own terms. Checking it beats trusting a string that happens to parse. Each raise names the case and what was wrong with it, so a failure is diagnosable rather than anonymous. Run over the six cases, the two ratios at the bottom would plausibly come out as:

pass rate                   0.67
agreement with labels       0.83  (5/6)
disagreement                refund-window-invented-sla: judged pass, labelled fail

What the two numbers are for

The first number is the fraction of answers the judge passed: four of six, here. It is the number that gets quoted in a standup, because it is about the system under test.

The second is the fraction of cases where the judge’s verdict matched the human label — five of six. It is not about the system under test at all. It is about the judge, and it is the thing that decides whether the first number means anything. A judge that agrees with you eight times in ten gets one verdict in five wrong, and if those errors lean one way the reported pass rate is off by up to twenty points. Until you have measured agreement you do not know how wide that band is, only that it exists.

Look at which case the judge missed and the point sharpens. It is the invented processing time — the hallucination wearing the documentation’s vocabulary, the exact failure this pipeline exists to catch. One disagreement in six is how you find out you haven’t caught it yet, and there is no way to find that out from the pass rate alone.

Which is what a typed verdict buys. Not a judge you can trust: a pipeline whose failures are the kind you can see. The verdict arrives as an object with a shape the harness checks, so a refusal, a truncated reply and a fenced-off blob of JSON all stop the run and name the case instead of being averaged into a number. Everything after that — the batch job, the two ratios — is ordinary code, and the judge is finally something you can measure rather than something you hope about.
