Some things you compute can be walked back and some cannot. Encode a file and you can decode it. Average a column and the original numbers are gone for good — no cleverness, no bigger machine, no second look at the average brings them back. The difference is not how hard the computation was; it is whether the answer still contains enough to say where it came from.

Recursion looks like it should land on the reversible side. A recursive function takes a problem apart one layer at a time until it hits something trivial, and a process that goes down in orderly steps feels like it ought to come back up the same way. It doesn’t follow, and the two examples below are structurally the same function with opposite answers.

Recursion and reversibility are unrelated questions

What decides the question is a property of the input–output pairing, not of the code. Ask whether two different inputs can ever produce the same output. If they can, then when you hold the output in your hand there is no fact of the matter about which input made it, and no inverse function exists — not one nobody has found yet, but one that cannot be written. A function where every distinct input lands on a distinct output is called injective, and injectivity is the whole of the question. The recursion is just the implementation. Which means the place to look is not the descent but what each step does with the piece it takes off.

Peeling bits keeps everything, so it inverts

Start with a step that takes a piece off and keeps it. The first example turns a whole number into its binary digits. At each step it takes the remainder on division by two — the last digit of the binary form, what computing calls the least-significant bit — records it, and hands the halved number back to itself. The base case is zero, which produces the empty list and stops. Its partner, from_binary, does the same walk in reverse.

Code 
def to_binary(n: int) -> list[int]:
    if n == 0:
        return []
    return [n % 2] + to_binary(n // 2)


def from_binary(bits: list[int]) -> int:
    if not bits:
        return 0
    return bits[0] + 2 * from_binary(bits[1:])


to_binary(13), from_binary(to_binary(13)), from_binary(to_binary(13)) == 13
([1, 0, 1, 1], 13, True)

It inverts cleanly because every recursive step keeps exactly the information needed to undo itself: the bit it just produced, plus a smaller version of the same problem. Nothing is merged or thrown away, and the base case — [], meaning “done” — is never confusable with an in-progress result. Rebuild bit by bit, in reverse order, and you are back where you started.

So to_binary is a bijection: a perfect pairing, each input matched to exactly one output and each output to exactly one input. That claim needs its domain stated to be true. The pairing runs between the non-negative integers and the bit lists this function can actually produce, which are the ones with no wasted zero on the end; hand from_binary a list from outside that set and you get an answer with no partner to go back to.

None of that came from the recursion, though, and the next function proves it by keeping the recursion and changing one operator.

Adding throws away exactly what peeling kept

total is the same shape of function — take the first item, combine it with the result of recursing on the rest, stop at the empty list. The only difference is what “combine” means. Here it means add, and addition is where the two examples part company.

Code 
def total(xs: list[int]) -> int:
    if not xs:
        return 0
    return xs[0] + total(xs[1:])


total([1, 2, 3]), total([3, 2, 1]), total([6])
(6, 6, 6)

All three return 6. Each step folds one element into a single running number and keeps nothing else about it — not its position, not its neighbours, only its contribution to the running total. A step like that is a lossy accumulator: what comes out is smaller than what went in, and the difference is gone rather than stored somewhere else.

So three different lists land on one number, and the question the first section asked answers itself. Two distinct inputs share an output, total is not injective, and there is no fact of the matter about which list “the” 6 came from. No inverse exists — not a missing feature, but a consequence of the combining step being many-to-one. Every recursive function with that property is in the same position, however tidily it descends.

Speculating: memory may be an accumulator too

Once you have the shape of a lossy accumulator in mind, it is hard not to notice how much of lived experience seems to have it. Perception and memory do not archive raw frames. They fold each moment into a running impression — a mood, a gist — discarding the order and the detail the way total discards which numbers summed to 6. Ask someone how their week was and you get a scalar, not a list.

That is speculation about minds, not a result about them, and nothing above establishes it. But it suggests a small and non-mystical reading of why experience feels irreversible: not that time refuses to run backwards, but that the encoding we hold experience in may be non-injective by construction, much like a sum.

Which is where the two functions leave the argument. to_binary and total descend the same way, recurse the same way, and stop the same way, and only one of them can be undone. What separates them is not the recursion but whether the answer still carries enough to say where it came from — and once a step has stopped carrying it, no later cleverness puts it back, because it was never kept.
