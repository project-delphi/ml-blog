# The Poor Person's Bayesian

Source for the blog post *"The Poor Person's Bayesian: the bootstrap moves the
data; Bayes moves the parameters."*

## Contents

```
index.qmd            the post (Quarto, knitr engine, all code in R)
styles.scss          post-scoped ink-and-paper theme, layered over the site's `zephyr`
cover.png            generated by the post itself (figure 2), used as the social card
images/
  munchhausen-swamp-hosemann.png   public-domain engraving
  attribution.txt                  artist, date, source URL, licence, provenance
```

`cover.png` is **written by the render** — the `fig-law` chunk calls `ggsave()` —
so it regenerates whenever the post is rebuilt. Do not edit it by hand, and do
commit it: because it is produced *during* execution, Quarto does not discover it
as a resource on its own, which is why the frontmatter names it explicitly:

```yaml
resources:
  - cover.png
```

Without that block the page still renders, but `cover.png` is never copied into
`docs/`, and the listing thumbnail and social-card image 404.

## Rendering

From the repository root:

```sh
quarto render posts/poor-persons-bayesian/index.qmd
```

or standalone, from this directory:

```sh
quarto preview index.qmd
```

The post is self-contained: it needs no Python, no Jupyter kernel, and no
per-post virtualenv. Quarto's `knitr` engine runs it through whatever R is on
`PATH`.

## Dependencies

R (≥ 4.0) plus:

| Package | Why |
|---|---|
| `knitr`, `rmarkdown` | Quarto's R engine |
| `boot` | `boot()`, `boot.ci()` for BCa; the `aircondit` data |
| `bootstrap` | the `law` (n = 15) and `law82` (population of 82) data |
| `ggplot2` | all nine figures |
| `dplyr` | light data wrangling |
| `patchwork` | multi-panel composition |

Install:

```r
install.packages(c("knitr", "rmarkdown", "boot", "bootstrap",
                   "ggplot2", "dplyr", "patchwork"))
```

Nothing exotic. Weighted quantiles are computed by a five-line CDF inversion in
the setup chunk rather than pulling in `Hmisc`, and the Dirichlet sampler is
three lines of `rexp()` — both are in the post because they are part of the
argument, not despite it.

## Reproducibility

Every resampling chunk calls `set.seed()` and states `B` explicitly; the seeds
are dates that mean something (1720 the Baron's birth, 1785 Raspe, 1979 Efron).
Chunk caching (`cache: true`) is on for the two expensive simulations — the
`law82` coverage study and the `n`-sweep — and the site-wide `freeze: auto` in
`posts/_metadata.yml` means an unchanged post is a no-op on re-render.

Every number quoted in the prose is interpolated from the code with inline R;
there are no hardcoded figures that could drift away from the computation.

## Notes on the toolchain

`styles.scss` is post-scoped via the frontmatter (`theme: [zephyr, styles.scss]`)
rather than added to the site-wide `_quarto.yml`, so it restyles this post only
and leaves every other post in the blog untouched. The repo's `_quarto.yml` and
root `styles.css` are deliberately unmodified.

One consequence worth knowing: the SCSS also darkens the navbar (`$navbar-bg`) to
the post's ink colour, because Zephyr's default cobalt fights the ink-and-paper
palette. That means this post's navbar does not match the rest of the blog. If you
would rather have site-wide consistency than per-post coherence, delete the three
`$navbar-*` variables near the top of `styles.scss`.

**Site-wide render:** at the time of writing, `quarto render .` (and any rebuild of
the homepage listing) fails on an unrelated post — `posts/skills-vs-commands/`
pins `jupyter: skills-vs-commands`, a kernel that is not registered locally. That
is independent of this post, which uses the knitr engine and no Jupyter kernel at
all, but it does mean the homepage listing cannot be regenerated until that kernel
is registered (see the repo `AGENTS.md` for the per-post venv/kernel convention).
